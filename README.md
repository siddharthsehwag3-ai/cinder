# Cinder

**Write it. Run it. Understand it.**

Cinder is an interactive C-subset compiler and bounded virtual machine written from scratch in C. It compiles and executes programs natively from the command line and inside the browser through WebAssembly.

The browser workbench lets users write C code, run it, inspect diagnostics, and explore the tokens, syntax tree, functions, types, and generated bytecode produced during compilation.

## Highlights

- Compiler and virtual machine written from scratch in C
- Handwritten lexer with source locations
- Recursive-descent parser
- C-style type system

- Native command-line compiler

## Compilation pipeline

```text
C source
  |
  v
Lexer
  |
  v
Tokens
  |
  v
Recursive-descent parser
  |
  v
Type checking and semantic analysis
  |
  v
Abstract syntax tree
  |
  v
Bytecode generator
  |
  v
Bounded virtual machine
  |
  v
Program output or source-linked diagnostic
```

The browser interface exposes the intermediate results created by this pipeline.

See [the architecture guide](docs/ARCHITECTURE.md) for implementation details.

## Virtual memory

Cinder programs execute inside a two-megabyte linear memory region managed by the virtual machine.

The memory model supports:

- Global storage
- Function-local storage
- Arrays
- Strings
- Structures
- Pointers
- Pointer arithmetic
- Typed 8-bit, 16-bit, and 32-bit loads
- Typed 8-bit, 16-bit, and 32-bit stores
- Memory initialization and copying

Visitor code never becomes native machine code. It is compiled into Cinder bytecode and executed by the bounded virtual machine.

## Safety limits

Cinder uses fixed resource limits to keep native and browser execution predictable.

| Resource | Maximum |
|---|---:|
| Source text | 64 KB |
| Standard input | 64 KB |
| Tokens | 16,384 |
| Syntax-tree nodes | 24,576 |
| Types | 4,096 |
| Symbols | 8,192 |
| Functions | 256 |
| Structures | 256 |
| Structure members | 4,096 |
| Enumerations | 256 |
| Enumeration values | 2,048 |
| Bytecode instructions | 49,152 |
| VM value stack | 16,384 values |
| Function-call depth | 256 |
| Executed instructions | 1,000,000 |
| Program output | 16 KB |
| Virtual memory | 2 MB |
| Structured diagnostics | 128 |

The browser also terminates and recreates the compiler worker when a compilation exceeds its configured time limit. This prevents a long-running program from freezing the main interface.

## Build

Run from the repository root:

```powershell
.\scripts\build.ps1
```

The build creates:

```text
build/cinder.exe
web/cinder.wasm
```

The native compiler is compiled in C11 mode with warnings treated as errors.

The same C compiler core is compiled to a freestanding WebAssembly module for browser execution.

## Run the native compiler

Compile and execute a Cinder program:

```powershell
.\build\cinder.exe .\tests\advanced-memory.c
```

Supply standard input using a text file:

```powershell
.\build\cinder.exe `
    .\tests\advanced-stdin.c `
    .\tests\advanced-stdin.txt
```

The native executable writes a JSON report containing:

- Success status
- Program output
- Return value
- Diagnostics
- Tokens
- Types
- Functions
- Syntax-tree nodes
- Generated instructions
- Execution-step count

## Run the browser application

Start the local static server:

```powershell
.\scripts\serve.ps1
```

Open:

```text
http://localhost:4173
```

Use the local server instead of opening `index.html` directly because browsers restrict WebAssembly loading from local files.

## Browser architecture

`compiler/cinder.c` is compiled into `web/cinder.wasm`.

`web/compiler-worker.js` owns the WebAssembly instance and performs compilation outside the browser’s main interface thread.

`web/app.js` manages:

- The code editor
- Compiler requests
- Worker lifecycle
- Execution timeout
- Diagnostics
- Source navigation
- Output rendering
- Token rendering
- Syntax-tree rendering
- Instruction rendering
- Interface rendering limits

The worker supports separate source and standard-input buffers. The visible standard-input editor is being integrated into the browser workbench.

Source code and program input remain inside the visitor’s browser.

- Invalid structure members

- Division or modulo by zero
- Invalid shift counts

- Stack exhaustion
- Excessive recursion
- Excessive execution
- Excessive output

## Current limitations

Cinder does not currently support:

- Complete ISO C compatibility
- Preprocessor directives
- `#include`
- Macros
- `typedef`
- Unions
- Bit-fields
- Floating-point types
- Function prototypes
- Function pointers
- Variadic user-defined functions
- Multiple translation units
- Dynamic memory allocation
- Standard library headers
- File APIs
- Network APIs
- Process APIs
- Native machine-code generation
- Every ISO C integer-promotion rule
- Every ISO C implicit-conversion rule
- Every undefined-behavior rule required by the C standard

Programs requiring complete C compatibility should be compiled using GCC or Clang.

## Deployment

Cinder is a static browser application and can be deployed through Vercel without a backend server.

Use these Vercel settings:

```text
Framework preset: Other
Root directory: repository root
Build command: leave empty
Output directory: web
Install command: leave empty
```

The committed `web/cinder.wasm` file is served together with the HTML, CSS, JavaScript, and Web Worker.

## Name

A cinder is a small piece of material that remains hot after a fire.

The name represents a compact compiler core that turns source code into something active and observable. It also matches the project’s dark interface, cyan highlights, and warm amber accent.
